计划日期：2026-09-28。实施更新：2026-09-29。状态：实现和本地自动化验证完成；已配置本地密钥并完成 Notes、相邻追问和天气拒答的真实模型验证，完整模型效果验收尚未完成。

## 1. 已确定的需求

| 项目       | 决定                                                                                                                                                                        |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 定位与范围 | 根据作者已有公开资料介绍本人、项目和文章，拒绝与作者无关的通用问答。不能因为文章提过 Go，就开放任意 Go 代码生成。                                                           |
| 事实依据   | 第一版只使用本站已有公开资料。不自动引入私有简历；阅读摘录、他人观点、计划不能改述为作者已完成的成果或本人立场。资料不足就说明。                                            |
| 项目       | 个人简介和全部五个项目每次进入模型资料；字段为 ID、名称、职责、摘要等必要信息，不传图标和 UI 样式。                                                                         |
| 文章入口   | Notes / Thoughts 分别选日期最新三篇，再从其余同类公开文章无放回随机选两篇，顺序为最新在前、随机在后；不足五篇按实际数量。允许跨次重复。目前 Thoughts 四篇，会展示全部四篇。 |
| 自由提问   | 先复用现有关键词检索，提供少量相关摘要和正文片段。接受漏选；“本次没有找到”不能表述为“作者从未写过”。没有文章命中仍可以用个人和项目资料回答。                                |
| 短历史     | 只发送上一轮成功完成的问答，以及最近一次实际展示的卡片 ID 和顺序。没有新卡片时保留原列表；有新列表时替换。指代不清就询问。                                                  |
| 会话       | 页面保留完整会话；同标签页站内导航保留，刷新、清空或关闭标签页重置。不做持久化、长期记忆或滚动摘要。                                                                        |
| 回答方式   | 四个入口与输入框统一调用模型，移除旧的预写回答与本地问答分流。system prompt 保持短小。                                                                                      |
| 流式与 Bot | DeepSeek 关闭推理，不新增 think 阶段。保留普通加载反馈、真实流式 response，删除模拟分块和等待时长。Bot 动作由请求实际状态驱动。                                             |
| 卡片       | 复用 ProjectCard / ArticleCard。标题、图标、链接来自真实目录；服务端验证引用。显示卡片不增加工具调用或第二次生成。                                                          |
| 不可用情况 | 未启用、限流和调用失败时明确提示，不自动退回预设回答；公开目录仍可访问。                                                                                                    |

成功标准：访客可以了解作者的真实经历，获得有效项目/文章卡片，并完成相邻追问；不输出无关通用答案、不伪造个人事实，历史和模型调用次数保持有界。

## 2. 技术选择与核验依据

采用 Vercel AI SDK，继续直连 DeepSeek。复用 SDK 的 provider、结构化输出解析、UI Message Stream 和 React 会话状态，不自写 SSE 协议或不完整 JSON 解析器。

| 依赖               | 用途                                | 2026-09-28 查询到的候选稳定版本 |
| ------------------ | ----------------------------------- | ------------------------------- |
| `ai`               | `streamText`、结构化输出、UI 消息流 | `7.0.118`                       |
| `@ai-sdk/deepseek` | DeepSeek 请求适配与关闭推理参数     | `3.0.54`                        |
| `@ai-sdk/react`    | `useChat`，消息、状态、取消及流接收 | `4.0.121`                       |
| `zod`              | 请求、输出及自定义消息数据的 schema | `4.6.5`                         |

以上版本已核对 npm 官方发布包：`@ai-sdk/react@4.0.121` 精确依赖 `ai@7.0.118`，provider / provider-utils 版本相容；Node >=22、React peer 声明与本站 Node >=22、React 19.3 的声明兼容。实现已安装并锁定这一组版本，使用真实 provider 和 SDK 对受控上游完成运行集成验证；不混用旧版 AI SDK 示例中的返回属性、回调名或实验接口。

一手依据：

- [AI SDK DeepSeek provider](https://ai-sdk.dev/providers/ai-sdk-providers/deepseek)：直接使用 DeepSeek API，支持 `thinking.type: disabled`。
- [结构化输出](https://ai-sdk.dev/docs/ai-sdk-core/generating-structured-data)：使用 schema 及 SDK 解析后的增量对象和最终输出。具体流对象属性以锁定版本的类型为准。
- [useChat](https://ai-sdk.dev/docs/reference/ai-sdk-ui/use-chat)：消息、submitted / streaming / ready / error 状态、停止和结束回调。
- [Transport](https://ai-sdk.dev/docs/ai-sdk-ui/transport)：可通过请求准备函数替换请求体，避免默认上传全部 messages。
- [自定义数据流](https://ai-sdk.dev/docs/ai-sdk-ui/streaming-data)：用固定 ID 的 `data-*` 消息部分更新业务数据。
- [DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)：推理开关与 stream 分开配置；JSON 模式不能替代本站的 schema 和 ID 校验。
- 本地 Next 文档 `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` 及 `05-server-and-client-components.md`：HTTP 路由用 Web Request / Response，正文读取与密钥仅在服务端。

模型继续使用当前 `deepseek-flash`，显式关闭推理。每次交互只做一次生成；关闭 SDK 自动重试，不配置自动续写、工具循环或模型降级。异常交由访客显式重试。

手写 system prompt 保持短小，但 DeepSeek provider 会为 JSON 模式将输出 schema 注入 system 消息；真实输入还包含这部分 token，费用记录不能只统计手写提示词。

## 3. 模块结构与依赖

```text
src/
  lib/
    answer/
      schema.ts           两端共享的请求、模型回答、自定义 UI 数据 schema 和类型
      context.server.ts   公开事实读取、文章选择、追问资料、上下文组装
      service.server.ts   短提示词、调用 SDK、最终校验、SDK UI 流业务映射
    projects/             现有项目事实数据
    writing/              现有文章 loader、公开类型与关键词检索
  app/
    api/answer/route.ts    HTTP 检查、请求体解析、调用回答模块、返回 SDK 流
    _home/
      topics.ts           入口标签、说明；引用共享的标准问题映射
      conversation.ts     SDK Chat、成功判定和短历史投影
      catalog.ts          从真实公开目录解析卡片引用，不生成回答
      use-conversation.ts 包装 useChat；短历史投影、清空、完成状态与 Bot 信号
      conversation-provider.tsx 共享布局内唯一会话宿主
      components/         消息、输入框和快捷入口的视图
  config/site.ts          网站与模型共用的公开个人资料
  components/             保留现有项目卡片、文章卡片及 Bot 模块
```

`lib/answer/schema.ts` 是浏览器可用的共享模块，包含 topic 与标准问题映射；另外两个文件标记 `server-only`。回答模块可读取 projects / writing / config；这些资料模块不反向依赖回答模块。`_home` 不导入任何服务端读取或 provider。路由不导入 `_home` 的实现。

`service.server.ts` 对路由提供一个回答入口，内部使用 SDK 和 context；不新增 provider 基类、通用 agent 框架、依赖注入容器或向量数据库。schema 类型用 Zod 推导，不同时手写另一套同义接口。

个人资料继续以 `site.ts` 为入口；About 页面中需要模型使用的现有公开介绍抽到共享配置，页面和模型共同消费。项目和文章摘要不复制、不在请求时调用模型重新生成。`content/` 仍由同步脚本管理，不把新维护资料写入其缓存目录。

## 4. 请求与短历史契约

`POST /api/answer` 请求体只包含当前动作、上一轮成功问答和最近卡片引用。当前动作使用互斥联合，快捷入口只提交 topic，自由提问只提交 text，拒绝在同一动作里混用两者。入口标准问题由服务端根据共享的 topic → question 映射派生，前端入口也使用这份映射；标签和图标仍在 `_home/topics.ts`。`previous` 不包含重复的卡片数据；不接受客户端上传的个人资料、文章正文、system 消息、工具描述或任意角色数组。

```text
question              { type: topic, topic: projects | notes | thoughts | about }
                      或 { type: text, text: 当前问题 }
previous?             { question, text }
lastShownReferences   [{ type: project | article, id }, ...]，保留原始展示顺序
```

- 前端使用 SDK Transport 的请求准备函数，从完整 UI 消息中提取上述字段；服务端用独立 schema 强制相同限制。
- 当前问题沿用 300 字符上限；上一轮问题最多 300、回答最多 1,200 字符；引用最多五条且无重复，ID 最多 80 个 ASCII slug 字符并在目录内验证（当前公开文章最长 ID 为 40 字符）。请求体上限设为 16 KiB，覆盖该有界结构的 UTF-8 / JSON 转义开销，仍按实际读取字节限制，不能仅依赖 Content-Length。schema 拒绝未知字段。
- 成功问答指有最终校验结果且 SDK 正常结束的一轮；中断、取消、失败、截断输出不进入有效历史。短拒答和澄清属于正常完成的对话，可以作为上一轮。
- 最近卡片从成功消息反向查找最近的非空引用列表，不为此建立第二份完整消息数组。
- 历史文本仅用于理解当前问题，不是作者事实。客户端历史可以被伪造，不能依据“上轮说过”新增作者的经历、观点或公开范围。
- 清空同时停止请求并重置消息、短历史和卡片引用；旧请求迟到的回调不能写回新会话。

## 5. 资料选择规则

一次请求在服务端通过现有 `getPublishedArticles()` / loader 读取同一份公开内容快照，供检索、上下文、ID 校验使用，避免另建 Markdown 扫描逻辑、多次读取或前后候选不一致。历史引用也必须属于这份快照；已撤稿、伪造和未知 ID 不允许载入正文或生成卡片。

### 5.1 明确入口

- Projects：提供全部项目，回答介绍对应项目；入口的展示列表由服务端固定为现有项目顺序。
- About：提供公开个人资料和项目背景，不强制附卡片。
- Notes / Thoughts：仅选对应类型；按日期降序，日期相同时按 ID 稳定排序。先取前三篇，再从剩余文章无放回选最多两篇。一次请求只抽样一次，提示词与最终展示共用这份列表。
- 入口的文章列表由程序选择，模型介绍该列表；只有正常 `kind=answer` 且最终结果有效时，最终引用使用这份服务端列表，确保不会因模型漏选变成不足五篇或改变“最新在前”的规则。`unmatched` 必须没有引用，入口也不例外；拒答、失败时不能强行附卡片。只有自由提问由模型从提供的候选中选择引用。

### 5.2 自由提问与追问

- 复用 `writing/search.server.ts`，按当前问题检索；普通问题最多三篇正文摘录，每篇沿用现有约 900 字符窗口。
- 最近展示的文章最多五条摘要可作为指代目录，与个人、项目资料分开标注。生成之前的确定性定位只支持：有效 ID、唯一精确标题、阿拉伯数字或中文一至五序号，以及最近列表只有一个对象时的“它 / 这篇 / 这个项目”。数字限定必须符合实际数量；越界不自动换对象。
- “第二个”按最近完整列表顺序；“第二篇 / 第二篇笔记”按该列表中文章的相对顺序；“第二个项目”按其中项目的相对顺序。列表过滤不改变同类条目的原展示次序，词义或类型仍有歧义时要求澄清。
- 确定目标后，复用 writing/search 的摘录能力读取正文；必要时为明确目标导出取摘录函数，不复制检索算法。若当前问题只有“展开讲讲”这类无正文关键词的短语，以上一轮有效问题辅助定位摘录，并如实说明只能依据所给片段。
- 不承诺任意自然语言指代解析：未满足上述唯一定位规则的指代，仅提供有界目录并要求澄清，不让模型先猜再触发第二次读取。普通有独立主题词且不含承接指代的问题只按本轮检索，不默认拼上旧问题，从而避免旧主题污染新话题。
- 明确追问目标优先占用正文摘录名额；总正文仍最多三篇，不在“已有三篇检索结果”之外再无限叠加历史文章。
- 没有文章命中不提前返回 unmatched；模型仍需根据个人/项目资料判断能否回答。检索命中也不是允许无关问答的凭证。
- 自由提问的引用只允许来自本次实际提供给模型的项目和文章资料，不能仅凭全站 ID 存在就通过；保留模型选择顺序，拒绝重复和未知引用。

## 6. 一次模型调用到 UI 的流

继续使用 `kind + text + references` 作为模型的业务回答结构，schema 限制长度、引用类型和数量。回答 text 与 previous.text 共用 1,200 字符上限常量，保证成功回答可进入下一轮历史；输出 token 上限在实施时留足结构化字段开销。kind 至少区分正常回答与不匹配/无法回答；没有关联的通用问题应简短拒绝，references 为空。

1. `service.server.ts` 获取上下文，用短 system prompt 约束本人范围、事实来源、语言、简洁程度和输出结构。公开文章中的文字和历史均作为资料，不作为改写这些规则的指令。
2. 调用 `streamText({ output: Output.object({ schema }), ... })`，设置 `providerOptions.deepseek.thinking.type = "disabled"`、`maxRetries: 0`、有界输出和总超时，并传递请求取消信号。不配置自动续写或 stream retries；`onError` 记录首个上游错误，不返回重试指令，也不依赖在该回调内 throw 来终止整个 UI 流。
3. 消费 `partialOutputStream`，仅映射 `typeof partial.text === "string"` 的字段。部分对象未经最终 schema 校验，不能直接视为完整 Answer；不把原始 JSON 文本转发给用户，也不自己解析断裂的 JSON。
4. 用 SDK `createUIMessageStream` 显式写入 `start`，再用固定 ID 的 `data-answer` 数据部分更新增量文字。增量部分只带 `status: streaming` 和当前 text；不暴露尚未校验的引用。
5. 消费完增量后，读取 `result.finishReason` 与最终 `result.output`。只接受 `finishReason === "stop"` 且本次未记录上游错误，同时要求最终 schema 通过、引用在本次候选中有效；入口列表按第 5.1 节应用服务端选择。即使 JSON 合法，`length / error / other` 也不能作为成功。`partialOutputStream` 不转发所有 provider error 事件，后续 stop 也可能覆盖先前 error 的终态；发生过错误时，必须从 UI stream 的 execute 抛出并拒绝完成，不能仅凭迭代结束或最终 stop 判断成功。
6. 全部验证通过后，将同一个数据部分更新为 `status: complete` 和完整回答，再显式写入 `finish { finishReason: "stop" }`；用 `writer.setOutcome({ status: "completed" })` 记录服务端正常终态。`execute` 返回本身不会自动完成这些步骤。异常交给 SDK 错误机制，不写成功 finish。
7. `useChat` 消费 SDK 协议和数据部分；视图展示 SDK 已存的最新 text。客户端只在完整业务结果、`finishReason === "stop"` 且 `isAbort / isError / isDisconnect` 全为 false 时确认成功、显示卡片和纳入短历史。`onFinish` 在失败和取消后也可能执行，不以回调发生作为成功信号。自定义数据 schema 同时接受 streaming / complete 两种形状。

正常协议顺序为 `start → data-answer(streaming) × N → 最终校验 → data-answer(complete) → finish(stop)`。业务数据完整但连接尚未正常结束的短暂状态，仍不触发成功表现。

这里使用 SDK 的标准自定义数据部分，只写少量业务映射，不新增一套自定义传输事件，也不增加工具调用。`useChat` 不会自动从任意 JSON 中挑出 text；上述业务映射不可省略。每次更新同一数据 ID，避免把每个增量变成一条新消息或一张新卡片。

模型范围限制通过资料隔离、短提示词和明确的拒答验收约束。Schema / 引用校验只能验证结构和引用，不等于证明自然语言一定正确；不能在审阅或测试报告中声称提示词提供绝对保证。

上述终态行为已核对锁定候选版本的源码：[UI stream 创建](https://unpkg.com/ai@7.0.118/src/ui-message-stream/create-ui-message-stream.ts)、[服务端 outcome](https://unpkg.com/ai@7.0.118/src/ui-message-stream/handle-ui-message-stream-finish.ts)、[客户端结束回调](https://unpkg.com/ai@7.0.118/src/ui/chat.ts)、[结构化输出](https://unpkg.com/ai@7.0.118/src/generate-text/output.ts)、[生成流](https://unpkg.com/ai@7.0.118/src/generate-text/stream-text.ts)。Schema 注入依据为 [DeepSeek 消息转换](https://unpkg.com/@ai-sdk/deepseek@3.0.54/src/chat/convert-to-deepseek-chat-messages.ts)。

## 7. HTTP、异常和会话生命周期

路由保留启用开关、同源、Content-Type、流式读取请求体的字节限制与 schema 校验。流开始前返回适当的 HTTP 错误；开始后用 SDK 错误机制结束，不再尝试改 HTTP 状态码。不把 provider 错误体或密钥返回浏览器。

- 未配置 / 503、429、上游失败：显示相应提示，不自动模型重试、不切回预设；保留目录导航。若上游错误发生在 UI 流开启后，由 service 映射成固定安全提示，客户端不能从已有 HTTP 200 推断上游状态码。
- 流中途失败：已显示文字标记为未完成，不显示卡片、不触发正常完成动作，不加入有效历史；允许重新提问。
- 前端仍允许起草下一问，submitted / streaming 期间禁止并发提交。ready 不是“本轮成功”的充分条件，需要有效最终结果及正常结束标记。
- 会话 Hook 挂在现有根布局 Provider 内；离开首页进入文章不会卸载会话，也不停止尚在接收的流。回来显示当时的真实进度或最终结果，不重播。
- 将 `request.signal` 与总超时信号组合后传给 `streamText`。清空和 Provider 卸载取消网络及上游生成；分别在 Next dev 与生产模式用受控上游验证取消贯通。`createUIMessageStream` 本身不会自动取消另一个生成任务，不启用后台消费或断线续传。
- `stop()` 不等待全部结束回调；清空须推进会话标识，并将成功标记、Bot 信号绑定当前会话/请求，忽略旧请求的迟到回调。
- Bot 在 submitted 时只保留普通加载反馈，不建立 think 动作；streaming 时响应；完成、拒答、失败分别映射现有表现。只有在当前页面新完成的正常回答触发一次完成动作，返回历史页面不重播。
- 随文字更新不强制滚回当前问题。仅在新轮开始定位到新问题；用户仍在底部时跟随输出，主动上滚后不抢位置。保留现有阅读返回滚动恢复与减少动态效果支持。
- 视觉流式与读屏播报分开：删除当前重复的全文 aria-live / 隐藏全文组合，不按每个增量重读整段；以普通加载状态、最终完整回答及错误作为播报时点，验证键盘与屏幕阅读器可访问性。

现有外部限流以 `docs/ai-answer-setup.md` 为已记录配置：主域名 10 秒一次、Vercel 直连 10 分钟六次，尚未重新核验线上。统一模型调用后快捷入口也消耗额度，真实连续追问必须在上线前核验；本计划不自动修改 WAF、部署或账户余额。该检查影响上线，不阻止本地功能与模拟流验证。

## 9. 实施顺序与检查点

1. **依赖与最小集成验证**：安装并锁定相容 SDK / Zod 版本。用受控上游响应验证“关闭推理 + 结构化部分对象 + UI 自定义数据流 + useChat”的真实类型和运行链路。特别检查 Unicode、JSON 转义、跨块数据、finish / error / abort，以及 SDK 7 与旧示例的差异。此步不调用真实付费接口，不为测试加生产路由。
2. **数据与契约**：建立 schema、共享个人资料和 context；实现最新三篇加随机两篇、普通检索、历史目标直接读取、请求体上限和候选引用校验。
3. **服务端回答**：建立单次生成流程，精简 route，移除无文章就提前拒答的路径。覆盖流前 HTTP 错误、流中错误、超时和取消。
4. **前端接入**：Provider 内接 useChat，加入短历史请求投影、成功标记和卡片数据映射，删除模拟播放与预设分支，接好 Bot、导航返回和滚动。
5. **文档与回归**：同步现行约定及导入规则；执行模块、构建、桌面/小屏端到端和页面实际检查。
6. **真实模型验收与上线检查**：在实现阶段按授权使用本地可用配置做少量真实问答，验证范围、资料依据与 DeepSeek 的实际结构化输出；记录真实 usage，不根据字符数宣称精确 token。没有可用配置时明确标记未验证，不以模拟通过代替模型验收。线上启用另核验 WAF 及连续追问行为。
